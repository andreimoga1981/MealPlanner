# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Meal planner made of one Supabase backend and two clients:
- `apps/web`: Next.js web admin where an admin logs in and manages recipes (the only place recipes are created)
- `apps/mobile`: planned Expo iPhone app (not created yet) that will read the same Supabase data
- `packages/shared` (`@meal-planner/shared`): zod recipe schema, the `ALLERGENS` list, types and pure helpers (time formatting, `ingredientLine`, family-size scaling and macro totals) shared by both clients. It is consumed as TypeScript source (no build step) via `transpilePackages` in `apps/web/next.config.ts`.

## Commands

npm workspaces; run from the repo root:

```bash
npm install
npm run dev      # web admin on :3000 (needs apps/web/.env.local)
npm run build    # production build of apps/web
npm run lint     # eslint for apps/web
```

Typecheck: `cd apps/web && npx next typegen && npx tsc --noEmit`. The global `PageProps<"/route">` / `LayoutProps` types are generated by `next typegen` (or by dev/build), so tsc fails on a fresh checkout without it. There is no test suite yet.

Env (`apps/web/.env.local`, template in `.env.example`): `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`, and server-only `GEMINI_API_KEY` (+ optional `GEMINI_MODEL`, a comma-separated list of models tried in order, default `gemini-3.5-flash,gemini-3.6-flash,gemini-3.5-flash-lite`; a 404/429/5xx/timeout falls through to the next). Without Supabase vars the proxy sends everything to `/login`, which shows a setup notice; without the Gemini key recipes still save with nutrition status `failed`. The Supabase CLI and Docker are not installed. The database is a hosted Supabase project, and the SQL in `supabase/` is applied by pasting it into the dashboard SQL Editor (setup steps are in README.md).

## Next.js 16 caveats

This is Next 16.4, not the Next.js in your training data. Read `apps/web/AGENTS.md` and the bundled docs in `node_modules/next/dist/docs/` before using framework APIs.
- Request interception lives in `apps/web/proxy.ts` (the `middleware` convention was renamed to `proxy`).
- `cacheComponents` / `partialPrefetching` are intentionally **off**: every page is per-request behind auth, so the request-time rendering model is used.
- `params` and `searchParams` are Promises; type pages with `PageProps<"/recipes/[id]">`.

## Architecture

**Auth (three layers):**
1. `proxy.ts` → `lib/supabase/proxy.ts` refreshes the Supabase session cookie and redirects signed-out requests to `/login`.
2. `lib/auth.ts` `requireAdmin()` (React `cache`d) verifies claims and `profiles.is_admin`. It is called in the `(admin)` layout, **every admin page and every server action**. Server actions must authorize themselves.
3. Postgres RLS (in `supabase/migrations/0001_init.sql`) is the real enforcement: signed-in users can read recipes (for the future phone app), but only `public.is_admin()` can write recipes or upload to the `recipe-images` bucket. `is_admin` can only be set via SQL, never through the API.

The login action (`app/login/actions.ts`) signs out non-admin accounts immediately.

**Saving a recipe:** `components/RecipeForm.tsx` (react-hook-form + `zodResolver(recipeInputSchema)`) runs in the browser. It uploads a chosen file directly to Supabase Storage with the browser client, then calls the `saveRecipe(id | null, input)` server action in `app/(admin)/recipes/actions.ts`. That action re-validates with the same schema and calls the `save_recipe(jsonb)` Postgres RPC, which inserts or updates the recipe and **replaces** all of its ingredients and steps in one transaction (array index → `position`). If saving fails, the client deletes the image it just uploaded. When a recipe's photo changes or the recipe is deleted, the server deletes the old file, but only if `storagePathFromUrl` (`lib/supabase/env.ts`) shows it's in our bucket; external URLs are left alone.

**Allergens:** `recipes.allergens text[]` holds ids from the fixed EU-14 list (`ALLERGENS` in the shared package; the same ids are in a DB check constraint, so change both together). The "Free from" filter *hides* recipes containing any selected allergen: `.not("allergens", "ov", "{milk,eggs}")` (GIN-indexed). The mobile app should use the same query. In the web admin the filter lives in the URL (`/recipes?q=…&free=milk&free=eggs`).

**Nutrition:** carbs/fat/protein are never entered by users and are not part of `recipeInputSchema`. `save_recipe` resets `nutrition_status` to `pending` for new recipes and whenever the ingredient list changes. `saveRecipe` then calls `calculateNutrition` (`lib/nutrition.ts`, server-only Gemini client) and writes whole-recipe grams plus `nutrition_status` (`ok`/`partial`/`failed`), `nutrition_skipped` (unrecognised lines) and `nutrition_error`. Gemini failures never block saving. One `generateContent` call with a JSON `responseSchema` returns per-line estimates (`recognised` + grams), which are summed server-side; unrecognised lines become `nutrition_skipped`. The `recalculateNutrition` action re-runs it. Every recipe is written for **one person** (there is no servings field; it was dropped in migration 0004), so stored macros are per person. The mobile app scales by family size with `scaleIngredients` / `macrosForPeople`, and `sumMacros` totals a meal.

**Data shape:** the DB stores `recipes` + `recipe_ingredients(position, quantity, unit, name)` + `recipe_steps(position, text)`. `lib/recipes.ts` `getRecipe` maps the joined rows into the shared `Recipe` shape (`ingredients[]`, `steps: {text}[]`; steps are objects because `useFieldArray` needs them). Migrations `0001`–`0004` are applied by hand, in order; the current `save_recipe` is the one in the highest-numbered migration that redefines it (now `0004_drop_servings.sql`). Schema changes go in a new numbered migration (copy that latest `save_recipe` and re-`create or replace` it when its payload changes), and must also update `packages/shared/src/recipe.ts`, `lib/recipes.ts` and the edit page's `RecipeInput` mapping.

Supabase clients: `lib/supabase/server.ts` (server components/actions, `server-only`), `lib/supabase/client.ts` (browser), `lib/supabase/proxy.ts` (proxy). The app uses no generated DB types; queries are untyped.

## UI conventions

- Tailwind v4. Design tokens are CSS variables in `app/globals.css` (light-green palette: `leaf`, `leaf-soft`, `accent`, `on-accent`, `line`, `muted`, … with dark-mode overrides), exposed as Tailwind colors via `@theme inline`.
- Shared component styles (`input`, `label`, `btn-primary`, `btn-secondary`, `btn-danger`, `panel`, `field-error`, `font-display`) are defined with `@utility`. In Tailwind v4, `@apply` of custom classes only works for `@utility` definitions, not for classes in `@layer components`. Avoid overriding their padding with extra utility classes, because utility ordering isn't guaranteed.
- Fonts: Bricolage Grotesque (`font-display`, headings) and Figtree (body), via `next/font/google` in `app/layout.tsx`.
- Icons are inline SVG components in `components/icons.tsx` (no icon library, no emoji). Recipe images use a plain `<img>` (arbitrary hosts) with the `no-img-element` lint rule disabled per file.
- UI copy uses sentence case ("My recipes", "Add recipe").
